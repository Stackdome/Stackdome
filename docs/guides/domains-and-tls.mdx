## Outcome

Expose an application at a Stackdome-generated public URL with HTTPS.

## Prerequisites

- A resource with an HTTP port.
- On Stackdome Cloud, no domain setup is needed.
- On self-hosted Stackdome, an organization domain and wildcard DNS that point to the installation.

## Use the CLI

For terminal, coding-agent, or CI steps, use [Expose a service with the CLI](/reference/cli-workflows#domains-and-tls).

## Dashboard workflow


Stackdome Cloud supplies the domain, DNS, and TLS. Mark a resource port public, deploy it, and use the URL shown on the stack.

On self-hosted Stackdome, your administrator supplies the organization domain and wildcard DNS. The rest of this page explains that setup and how Stackdome creates hostnames.

### Dashboard prerequisites

- **Access to the Stackdome dashboard.** During alpha, every signup owns one organization and uses its default project, so there is no role or project-selection step.
- **For self-hosted Stackdome, a domain whose DNS you control.** The installer can also use a `nip.io` trial domain.
- **For Stackdome Cloud, no domain work is required.** Skip to [Generated hostnames](#generated-hostnames).

## Self-hosted organization domain

The domain is a property of the organization, not of a stack or a **cluster**. There is one, and generated hostnames are built under it.

The installer sets the first domain. It uses the value passed to `--domain`, or a `stackdome.<PUBLIC_IP>.nip.io` trial domain. A new self-hosted installation normally needs no extra dashboard step.

To see it, open **Domains** under **PLATFORM** in the sidebar, at `/domains`.

![The Domains page in the Stackdome dashboard, with Domains highlighted under PLATFORM in the sidebar and the page headed PLATFORM Domains above the subtitle Configure custom domains for your organization, and an ALL DOMAINS panel counting 2 rows — stackdome.io and test.com — each with a globe icon](/images/domains-list.png)

Each row is a globe icon, the domain, and a trash icon. The trash icon removes the domain **immediately** — there is no confirmation step.

### Adding one

Choose **Add Domain**. The dialog is a single field:

| Field | Notes |
| --- | --- |
| **Domain Name** | Required. Placeholder `example.com`, hinted *"Examples: example.com, subdomain.example.org, app.company.co.uk"*. Lowercased and trimmed before it is saved. |

It has to be a fully qualified domain name: at least one dot, a top-level label of two or more letters, each label alphanumeric with hyphens allowed only in the middle, and 253 characters at most. Anything else stays in the form — an empty field is `Domain name is required`, a malformed one is `Please enter a valid domain name`, and one you already have is `This domain already exists`.

Adding or removing a domain rewrites the organization's whole domain list in one request. That is normally invisible, but it is why a failure here surfaces as a **Failed to update domains** toast rather than a per-row error.

<Warning>
**Keep exactly one domain.** Once one is configured, the **Add Domain** button is disabled and hovering it explains why: *"Currently only one domain is supported."*

![Close-up of the Domains page header: the Add Domain button greyed out, with a tooltip above it reading Currently only one domain is supported](/images/domains-add-limit.png)

That cap lives in the dashboard, not in the API — the API will store more than one, so an organization can end up holding several. When it does, generated hostnames are built under whichever one the database returns first, and that query has no ordering, so which domain wins is not something you can rely on. If the list holds more than one row, delete the extras.
</Warning>

## DNS

Two kinds of name have to resolve to the same place: the dashboard's own name, and every hostname Stackdome generates for a **resource**'s public **port**, all of which sit beneath it.

For the dashboard, an `A` record is enough:

```text
example.com.   A   203.0.113.10
```

Generated hostnames sit **two labels below** the domain — `<prefix>.<resource>.example.com` — so a record for the dashboard alone does not cover them. Add a wildcard:

```text
*.example.com.   A       203.0.113.10
*.example.com.   CNAME   example.com.
```

Either form works; use one, not both. A DNS wildcard answers for names at any depth beneath it, not just one label down, so a single `*.example.com` covers every hostname Stackdome will ever generate. That is verified against a live install: a two-labels-deep name under a wildcard `CNAME` resolves to the same address as the apex.

<Note>
A wildcard is matched against the closest ancestor of the name that actually exists in the zone. So if you later create a record for `web.example.com` in its own right, `*.example.com` stops answering for `<prefix>.web.example.com` — the generated hostnames for a resource named `web` go dark. If you want a vanity name for a resource, put it somewhere the wildcard does not shadow, or add the explicit records for the generated names too.
</Note>

Two more things to open, both on the server your cluster runs on:

- **Port 443**, for the traffic itself.
- **Port 80**, because certificate validation happens over HTTP. See below.

## Generated hostnames

Only a **public** port gets a hostname. An internal port is reachable inside the stack and has no name outside it. Nothing you do on the Domains page changes that — it is the port's **Expose to public** setting, on the resource in **the drawer**.

The pattern is:

```text
<generated-prefix>.<resource-name>.<organization-domain>
```

The prefix is derived, not random. Stackdome takes the stack's ID, the resource's name and the port number, joins them with colons, MD5s that, base32-encodes the digest with the standard alphabet and no padding, lowercases it, and keeps the first 16 characters.

You can reproduce it:

```bash
STACK_ID=f4c1e2a0-6b52-4a5e-9d3f-8c7b1e0a2d64
RESOURCE=web
PORT=3000
printf '%s:%s:%s' "$STACK_ID" "$RESOURCE" "$PORT" \
  | openssl dgst -md5 -binary \
  | base32 | tr -d '=' | cut -c1-16 | tr 'A-Z' 'a-z'
# ba6xykaf6wkmco2c
```

So a stack with that ID, holding a resource named `web` with public port `3000`, on an organization whose domain is `example.com`, is served at:

```text
ba6xykaf6wkmco2c.web.example.com
```

Two consequences follow from the inputs:

- **The hostname is stable.** Redeploys, rollbacks and edits to anything else leave it alone, because none of the three inputs change. The stack ID in particular survives everything short of deleting the stack.
- **Renaming the resource or changing the port number changes the hostname.** The name is part of the input twice — once in the hash, once as the second label — so a rename gives you a new hostname and retires the old one. Change the port number and the prefix changes too. Treat a rename as a URL change.

The stack header lists the public endpoints it has as a pill — the resource name and the hostname — and it links straight out to it. A resource with a public port also gains `public_host` and `public_url` outputs, which is the supported way for another resource to refer to it without you pasting the hash anywhere.

<Note>
**A fixed prefix, through the API only.** A public port accepts a `subdomain_prefix`. Set it and the hostname becomes `<subdomain_prefix>.<organization-domain>` — one label, and the resource name drops out. There is no field for this in the drawer; it is only reachable through the API. Two ports in the same stack asking for the same prefix are rejected with `subdomain_duplicate`.
</Note>

## Verify TLS

Run:

```bash
stackdome status --conditions
```

For a TLS-eligible public hostname, the resource condition `TLSConfigured` must be `True` with reason `TLSReady`. This is Stackdome's certificate-readiness signal; you do not need to inspect certificate-management resources directly.

Structured status includes resource conditions under `live_status.resources.<resource>.conditions`. The `--conditions` flag expands the human-readable table; it does not change the JSON object.

Hostnames ending in `.nip.io`, `.sslip.io`, `.local`, or `.localhost` are non-TLS trial names and do not receive a certificate.

## Dashboard and self-hosted troubleshooting

**The hostname resolves but nothing is served.** The port is internal. A hostname is only generated for a port marked public, so if you are guessing at a hostname for an internal port, there isn't one. Open the resource in the drawer, check the port, and confirm it appears in the stack header's public endpoints afterwards. If the header lists no endpoint, no public port exists.

**A resource with a public port refuses to deploy, complaining about domains.** The organization has none configured. Stackdome cannot build a hostname without one, and the failure reads `no domains found for organisation <id>`. Add one on `/domains`.

**TLS is not ready.** Run `stackdome status --conditions` and read the resource's `TLSConfigured` reason and message. Confirm the hostname resolves to the Stackdome installation and that public traffic can reach it. Do not report HTTPS success until the condition is `True` with reason `TLSReady`.

**A URL that used to work now 404s.** Someone renamed the resource or changed the port number. Both are inputs to the generated prefix, so both mint a new hostname. Read the current one off the stack header.

**HTTPS breaks after you change the organization domain.** Generated hostnames are rebuilt from the organization's domain, so changing it changes every hostname the next time a resource is saved. Update DNS for the new domain, and expect fresh certificates to be requested for the new names.
